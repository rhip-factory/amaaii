# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Amaaii is a maternal-health companion for pregnant/postpartum mothers in Kenya, reachable on two surfaces that share one brain and one identity (users keyed by `phone_number` = the raw `whatsapp:+E.164` string): a Twilio-sandbox WhatsApp bot and a PWA. The bot gives AI-generated support, detects pregnancy danger signs deterministically, and runs a multi-step daily journaling flow; the PWA adds OTP login, a structured check-in form, offline sync, and insights charts. Both surfaces sit behind a Kenya DPA-shaped consent + data-rights layer (Phase 3): two-tier consent, an append-only audit ledger, and self-service export/erasure — see "Consent, audit, and data-subject rights (Phase 3 / Kenya DPA)" below. Phase 4 (pilot hardening) added a durable SQLite job queue and pilot-grade observability (structured logging + correlation ids, `/metrics`, `/health`/`/health/ready`, a global error handler, and an alerting seam) — see "Durable job queue & observability (Phase 4)" below.

## Layout (TypeScript monorepo)

- `packages/core` — pure domain logic, no I/O, deterministic given inputs. Modules: `dangerSigns` (regex triage engine), `journal` (stage-machine transitions + parsers + summaries), `onboarding` (name/week/LMP parsers, EDD), `i18n` (EN + `sw` canned copy), `trend` (`computeTrend`, `computeDailySeries`, `computeSymptomCounts`, `computeRedFlagDates`), `redaction` (LLM/log PII masking — read its FIRST-NAME POLICY header before touching), `otp` (rate-limit/expiry decisions, no crypto), `consent` (two-tier consent decisions — `CONSENT_VERSION`, `deriveConsentState`, `needsConsent`, `canUseAi`, `hasActiveConsent`, `isStale`; pure, no I/O, same pattern as `otp`), `jobs` (Phase 4 — pure backoff/retry/due-ness decisions for the durable job queue: `computeBackoff`, `nextRunAt`, `shouldRetry`, `isDue`, `JOB_BACKOFF_SCHEDULE_MS`, `DEFAULT_JOB_MAX_ATTEMPTS`; same "no `Date.now()` inside, `now` passed explicitly" discipline as `otp`), `repositories` (interfaces, incl. `ConsentRepository`/`AuditRepository`/`JobRepository`/`eraseUser`), `types`.
- `packages/adapters` — I/O implementations: `sqlite/` (one repository class per table + `connection.ts` schema/migrations, incl. `consentsRepository.ts`, `auditRepository.ts`, `jobRepository.ts`, `erasure.ts`), `twilio.ts` (lazy client, `__setSendImpl` test seam), `llm.ts` (the single OpenAI chokepoint — see below).
- `apps/server` — Express in TS. Entry `apps/server/src/index.ts` (import order load-bearing: `register-paths` → `dotenv/config` → app). `app.ts` is the `createApp()` factory with all routes; `database.ts` is a stable facade over the SQLite adapter; plus `messageHandler`, `journalManager`, `userManager`, `amaaii` (prompts + AI reply), `llmExtract`, `trend`, `auth`, `otp` (crypto half), `audit` (`recordAuditSafe`, `auditDangerEscalation`, `wasAccountDeleted` — see Phase 3 section below), `logger` (PII-redacting), `jobWorker` (Phase 4 — poller + handler registry over the durable job queue, see below), `metrics` (Phase 4 — Prometheus text exposition), `alerts` (Phase 4 — `notifyCritical` webhook/log seam), `errorHandler` (Phase 4 — global Express error-handling backstop), `middleware/twilioSignature`, `middleware/requestObservability` (Phase 4 — correlation id + structured request logging + HTTP metrics).
- `apps/web` — Next.js 15 static-export PWA (the only pnpm workspace package; `packages/*` have no package.json and resolve via root tsconfig paths / vitest aliases / `register-paths.ts` for compiled dist).
- `tests/` — root vitest suite (414 tests) with golden fixtures (`danger-signs-golden.json`, `redaction-golden.json`). `scripts/smoke/` — shell E2E scripts, DB-isolated via scratch `DB_PATH`.

The older vanilla-JS PWA that used to live at `public/` is **retired** (express-serves-pwa): Express now serves the Next.js static export (`apps/web/out`) at `/` instead — single-process, single-origin deployment (see Architecture below). `public/` is gone from the working tree but recoverable from git history if ever needed.

## Commands

pnpm only (`packageManager: pnpm@10.33.0`; `sqlite3` is in `pnpm.onlyBuiltDependencies` — `npm install` can leave the native module unbuilt).

- `pnpm install`
- `pnpm dev` / `pnpm start` — Express server via `tsx` (watch / no-watch), port from `PORT` (default 3000). Serves the API always; serves the PWA at `/` too if `apps/web/out` exists (see "Serving the PWA" below).
- `pnpm test` / `pnpm test:watch` — vitest (414 tests in `tests/`)
- `pnpm typecheck` — `tsc --noEmit` over packages + apps/server (apps/web has its own `pnpm --filter web typecheck`)
- `pnpm build` — `tsc -p tsconfig.build.json` → `dist/`; boot the artifact with `node dist/apps/server/src/index.js` (works because of `register-paths.ts` + `paths.ts` — see their headers before touching import resolution)
- `pnpm dev:web` — `next dev` for the PWA; point it at a running API with `AMAAII_API_ORIGIN`, e.g. `AMAAII_API_ORIGIN=http://localhost:3100 pnpm dev:web` (rewrites proxy API calls in dev)
- `pnpm build:web` — static export to `apps/web/out`. **TRAP:** `next build` always writes into the literal `.next/` even with `NEXT_DIST_DIR` set, so it clobbers a running `next dev`'s state — build only in an isolated git worktree (documented in `apps/web/next.config.ts`).
- **Production shape (single process, single origin):** `pnpm build:web && pnpm start` (or `pnpm build:web && pnpm build && node dist/apps/server/src/index.js`). `apps/web/out` lives inside the source tree, not under `dist/`, so it's reachable identically from a `tsx` dev boot or a compiled `dist/` boot — `paths.ts`'s `WEB_OUT_DIR` walks up from `__dirname` to the repo root the same way `PUBLIC_DIR` used to, so the extra `dist/` nesting doesn't change the resolved path. Leave `NEXT_PUBLIC_API_ORIGIN` **unset** for this shape — `apps/web/src/lib/api.ts` then calls relative paths (`fetch("/insights")`, not `fetch("https://.../insights")`), which land on the same Express origin serving the page. Only set it when the static export is deployed separately from the API (e.g. a CDN-hosted `out/` calling a remotely hosted Express).
- Smoke suite: `PORT=4690 bash scripts/smoke/run-all.sh` — each script boots its own server on `$PORT` (default 3000; override when 3000 is busy) against a scratch DB. Never touches `./amaaii.db`. The smoke scripts never run `pnpm build:web`, so `apps/web/out` won't exist under them — `GET /` in that context is the plaintext build notice, not the app (still 200). `scripts/smoke/lib/send.sh#wait_for_server` polls the port (up to ~25s) instead of a fixed `sleep 2` before each script's assertions run — added in Phase 4 because boot time crept past 2s under load once the durable job worker started registering handlers and polling at boot (P4-A), which made the old fixed sleep racy.
- `ngrok http <port>` — expose `/webhook` for the Twilio sandbox.

There is no linter. Do not add one unless asked.

## Environment (`.env`)

- `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_NUMBER` — **optional**: both the Twilio and OpenAI clients are lazy, so the server boots without any credentials. With Twilio creds absent, `/auth/otp/request` switches to dev mode (code logged + returned inline as `devCode`, only when `NODE_ENV !== 'production'`).
- `OPENAI_API_KEY` — lazy too; AI replies fail at call time (with a canned fallback), not at boot.
- `PORT` — default 3000.
- `AUTH_SECRET` — HMAC secret for PWA bearer tokens and OTP code hashes (insecure dev default if unset).
- `DB_PATH` — SQLite path, default `./amaaii.db`. Read at module load: set it before anything imports `apps/server/src/database.ts` (tests set `:memory:` first).
- `TWILIO_SIGNATURE_ENFORCE` — `true`/`false`/unset; unset enforces webhook signatures only when `NODE_ENV=production`.
- `AMAAII_API_ORIGIN` — dev-only: where `next dev`'s rewrites proxy API calls (default `http://localhost:3000`).
- `NEXT_PUBLIC_API_ORIGIN` — baked into the static export at build time. Leave unset for the normal single-origin deployment (Express serves both `out/` and the API on one port, so relative `fetch()` calls already land in the right place); set it only when `apps/web/out` is deployed to a different origin than the API (no server, no rewrites at that point).
- `PUBLIC_BASE_URL` — optional, read at call time (not module load) by `messageHandler.ts#privacyNoticeUrl()`. When set, the WhatsApp consent request/reprompt copy links to `${PUBLIC_BASE_URL}/privacy`; when unset, it falls back to the generic phrase "the Amaaii app" instead of a broken/placeholder URL. **Currently unset in every environment this repo has been run in** — deferred: set it once the PWA has a real public hostname (see Aspirational-vs-actual / deferred items).
- `JOB_POLL_MS` — Phase 4. Poll interval (ms) for the durable job-queue worker (`jobWorker.ts#startJobWorker`), read lazily at call time so tests that set it after import still take effect. Default `15000`. A test/E2E harness typically lowers this (e.g. `2000`) to observe a poll cycle without waiting 15s.
- `METRICS_TOKEN` — Phase 4. Bearer token required on `GET /metrics` (`Authorization: Bearer <token>`), checked in **any** environment when set. When unset: served openly in non-production (dev/CI/smoke convenience) but `404`s in production — an unauthenticated pilot deploy should never expose request-volume/route-shape/job-count data to the open internet by accident.
- `ALERT_WEBHOOK_URL` — Phase 4, optional. When set, `alerts.ts#notifyCritical` fire-and-forget POSTs a small PII-free JSON payload (`{ event, message, requestId, timestamp }`, `message` redacted) to this URL on every critical alert (global error handler backstop hits, job-queue failure-threshold breaches). Point it at a Slack incoming webhook or an on-call tool's HTTP intake. **Always** logs an ERROR-level line regardless of whether this is set — see "Alerting is proportionate, not a platform" below.
- `JOBS_FAILED_ALERT_THRESHOLD` — Phase 4, optional. Minimum job **execution** failures (retryable + permanent, counted together) within a single poll cycle before `jobWorker.ts#runOnce` calls `notifyCritical('jobs_failed_threshold', ...)`. Default `3`.

## Architecture

Every inbound message (Twilio `POST /webhook` → `app.ts` → `messageHandler.ts#handleIncomingMessage`) runs `processMessage(from, message, profileName, opts)` — **the shared brain**, also called by the PWA's `POST /chat` (which passes `{ channel: 'web' }`). Routing priority inside it:

1. CRITICAL danger signs short-circuit **everything** — canned escalation copy, AI bypassed, and (Phase 3) the consent gate too: this is the one path that fires regardless of a user's consent state, the Kenya DPA vital-interests lawful basis. See "Danger signs always escalate" under Non-obvious points.
2. Non-CRITICAL messages from a user who hasn't granted the REQUIRED `data_processing` purpose hit the **consent gate** (`needsConsent()`, `packages/core/src/consent.ts`) — HIGH/MODERATE danger copy is still prepended here, same as onboarding below. WhatsApp: stateless conversational request/reprompt, keyed off the bot's last message (reply `I AGREE`/`NAKUBALI` grants both purposes at once). Web: `POST /chat` returns `{ consentRequired: true }` instead of routing further — the PWA's `/consent` screen handles it with two separate toggles (`useConsentGuard.ts` catches it proactively; the server-side check is the actual enforcement).
3. Un-onboarded users → stateless onboarding (HIGH/MODERATE danger copy is prepended, not dropped).
4. Active journal session or journal command → `journalManager.ts` stage machine (persisted in `journal_sessions`, survives restart; week ≥ 20 adds fetal movement; multiple check-ins/day).
5. `journal summary` / `weekly summary` / `doctor report` commands.
6. Otherwise `detectDangerSigns` (HIGH also escalates with canned copy) else, if the OPTIONAL `ai_responses` purpose is active (`canUseAi()`), AI reply via `amaaii.ts` with last-5-turn history, 7-day trend line, and medical history in the system prompt — otherwise the canned `ai_off_reply` string, and the LLM chokepoint is never called (`ProcessMessageResult.aiUsed` records which happened, for audit purposes only — not returned in `POST /chat`'s JSON body).

`handleIncomingMessage` adds WhatsApp delivery plus a follow-up for critical/high urgency — as of Phase 4 (P4-A) this is a **durable** SQLite-backed job (`checkin_followup` type, see "Durable job queue & observability (Phase 4)" below), not an in-process `setTimeout`. A follow-up scheduled before a server restart or crash still fires afterward: the job row survives in the `jobs` table and the poller resumes it on the next boot's first poll cycle. (This corrects an earlier version of this doc, which described the follow-up as "in-process and lost on restart" — that was true through Phase 3 and is no longer true.)

Web API (all in `app.ts`; bearer auth unless noted): `POST /auth/login` (legacy phone-only demo login, kept for back-compat), `POST /auth/otp/request` + `/auth/otp/verify` (real flow — verify also `getOrCreateUser`s, so the row exists before the client's first `GET /me`), `POST /chat`, `GET /me` (read-only — see "Post-delete read hardening" below for why it's no longer a plain `getOrCreate`), `PUT /me` (still `getOrCreate`s — legitimate first-touch profile save), `GET/POST /me/medical-history`, `GET /history`, `POST /journal/entries` + `GET /journal/entries?days=N` + `GET /journal/today`, `GET /insights?days=14|30` (400 on anything else). Phase 3 additions: `GET/POST /me/consent` + `POST /me/consent/revoke` (consent ledger), `GET /me/activity` (own audit-log read), `GET /me/export` (data portability, downloads a JSON attachment), `DELETE /me/account` (erasure — see below). Phase 4 additions — unauthenticated ops endpoints, mounted ahead of every other route: `GET /health` (liveness), `GET /health/ready` (readiness — pings SQLite, 503 on failure), `GET /metrics` (Prometheus text, gated by `METRICS_TOKEN` — see Environment above and the Observability section below). `/webhook` is guarded by `middleware/twilioSignature.ts`. `/privacy` is a public, unauthenticated page in the static export (no API route — plain content).

### Serving the PWA (`apps/web/out`)

`createApp()` checks for `apps/web/out/index.html` at boot (via `paths.ts`'s `WEB_OUT_DIR`) and switches behavior accordingly:

- **Built:** hashed `_next/static/*` assets get a long, immutable `Cache-Control` (safe — the filename changes every build); `sw.js` gets `Cache-Control: no-cache` so browsers always revalidate it and pick up service-worker updates promptly (see the SW-takeover note below); everything else in `out/` is served at its exact path via `express.static`. A GET fallback then maps extensionless routes to the export's flat `<route>.html` files (`next.config.ts` has no `trailingSlash`, so the export is `login.html`, not `login/index.html`) — both `/route` and `/route/` resolve the same way, and `/` resolves to `index.html`. Anything that still doesn't match gets the export's `404.html` with a real 404 status.
- **Not built** (dev/CI/smoke boots that never ran `pnpm build:web`): `GET /` returns 200 with a short plaintext notice pointing at `pnpm build:web` / `pnpm dev:web`, instead of pretending the app is there. `scripts/smoke/00-server-boot.sh`'s root check stays truthful under this.
- **Tests:** `createApp({ webOutDirOverride })` (see `CreateAppOptions` in `app.ts`) lets `tests/app.test.ts` point at a tiny fixture directory or a deliberately-missing path, so both branches are deterministic regardless of whether a real `apps/web/out` happens to exist on the machine running the suite.
- **Path traversal:** the extensionless-route fallback resolves `req.path` to a filename under `out/` — never build an absolute path yourself (`path.join(webOutDir, someRequestDerivedString)`) and hand it to `sendFile`; `req.path` is NOT normalized against `..` by Express (only browsers resolve `..` before sending — a raw client can send it literally, confirmed with `http.request({ path })`). Always pass a relative name + `{ root: webOutDir }` to `res.sendFile`, which delegates the boundary check to Express's `send` dependency. `tests/app.test.ts`'s "path traversal protection" block drives real sockets (not supertest, which normalizes `..` client-side before a request is ever sent) against a fixture with a planted secret file one level above the fixture's `out/` to pin this.

## Consent, audit, and data-subject rights (Phase 3 / Kenya DPA)

Two-tier consent, keyed by phone like everything else, lives in `packages/core/src/consent.ts` (pure decisions) + the `consents` table (append-only ledger — every grant/revoke is a new row, never an UPDATE) via `packages/adapters/src/sqlite/consentsRepository.ts`:

- `data_processing` — **REQUIRED**. The app has no lawful basis to keep operating for a user without it. `needsConsent(state)` is true until this purpose has an active grant.
- `ai_responses` — **OPTIONAL**. Gates only the LLM chokepoint (`canUseAi(state)`); declining it still leaves journaling, danger detection, and the deterministic reply flow fully working (the `ai_off_reply` canned copy, i18n'd EN/SW).
- `CONSENT_VERSION` (currently `1`) — bump it to force re-consent everywhere: `isStale(state)` compares each purpose's recorded `version` against the current constant; `needsConsent`/`isStale` together are what `useConsentGuard.ts` (web) and the WhatsApp gate re-check every session.
- Revoking `data_processing` (`POST /me/consent/revoke`) is a separate, deliberately-worded action from declining it in the bulk `POST /me/consent` body (which 400s on `data_processing: false` and points at `/revoke` instead) — a user can't withdraw REQUIRED consent by accident via the grants endpoint.

**Enforcement sits in the shared brain** (`messageHandler.ts#processMessage`), not just at the HTTP edge — see the Architecture routing list above for exactly where the gate sits relative to danger-sign precedence (after the CRITICAL bypass, before onboarding). WhatsApp and web diverge on granularity: WhatsApp's `handleConsentGate` is a stateless conversational back-and-forth (mirrors the onboarding pattern — infers "have I already asked?" from the bot's own last message) that grants **both** purposes together on an affirmative reply (`I AGREE`/`NAKUBALI`), since the WhatsApp bot *is* an AI chat with no meaningful "use it without AI replies" mode. The web PWA gates via `POST /chat` returning `{ consentRequired: true }` and lets the user grant the two purposes independently — the `/consent` screen for the initial gate, the Profile "Privacy & data" AI toggle afterwards.

**Danger signs always escalate — the vital-interests carve-out.** `processMessage` computes `detectDangerSigns(message)` (`earlyDanger`) BEFORE it looks at consent state at all; a CRITICAL result returns immediately, bypassing the consent gate, onboarding, journaling, and the AI/off branch entirely. HIGH/MODERATE danger copy is still prepended even while consent is outstanding (in both the web `consentRequired` response and the WhatsApp gate's reprompt) — declining consent, or never having been asked yet, must never silence an escalation. This is load-bearing: don't let a future consent-gate refactor move the danger check to run *after* the gate.

**Audit logging** (`apps/server/src/audit.ts`) is a separate table from the consent ledger: `recordAuditSafe(event)` writes an append-only row to `audit_log` (`actor`, `action`, `resource`, `resource_owner`, `metadata`, `created_at`) and swallows its own errors — a logging failure must never break the user-facing request. Call sites cover every data-access path: profile/journal/insights/medical-history reads and writes, consent grants/revokes, `/me/export`, `DELETE /me/account`, `ai_call` vs plain `write` on `/chat` (mirrors `ProcessMessageResult.aiUsed`, which the HTTP response itself never echoes back to the client), and `danger_escalation` (actor `'system'`, fired by `auditDangerEscalation()` for CRITICAL/HIGH only — the deterministic engine's own automated decision, not a user-initiated data access). `GET /me/activity` is the PWA's read of a user's own log ("who's accessed your data" on Profile); `GET /me/export` includes the complete log as part of the portability bundle. **`audit_log` is the one table `eraseUser()` deliberately does NOT clear** (see its doc comment in `packages/core/src/repositories.ts`) — the erasure event itself, and everything before it, survives the erasure it describes. This retention is exactly what P3-E's post-delete read hardening leans on — see the dedicated Non-obvious point below.

**Data-subject rights**: `GET /me/export` gathers profile, consents, conversations, journals, symptoms, ANC visits, medical history, and the complete audit log (everything except `otp_codes` — short-lived auth material, not portable "data about you") into one JSON document served as a downloadable attachment. `DELETE /me/account` is `eraseUser()` — a transactional hard-delete cascade across every user-owned table (again, except `audit_log`), idempotent by construction (a second delete on an already-erased phone deletes zero rows from each table and still returns `200 {deleted:true}`). Both are wired into the Profile "Privacy & data" section (`apps/web/src/components/PrivacySection.tsx`): export triggers a blob-download workaround (an authed endpoint can't back a plain `<a href>`); delete requires typing `DELETE` to confirm and always sends an explicit empty body (the server 400s if the body carries a `phone` key at all — the erasure target is always the bearer token's own phone, never client-supplied).

New tables (`packages/adapters/src/sqlite/connection.ts`): `consents` (append-only grant/revoke ledger) and `audit_log` (append-only, survives erasure).

## Durable job queue & observability (Phase 4)

**Durable job queue (P4-A).** A `jobs` table (`packages/adapters/src/sqlite/jobRepository.ts`, schema in `connection.ts`) replaces in-process timers for anything that must survive a restart. Pure scheduling decisions — backoff, retry-or-give-up, due-ness — live in `packages/core/src/jobs.ts`, same "no `Date.now()` inside, `now` passed explicitly" discipline as `otp.ts`/`dangerSigns.ts`:

- **Backoff**: `JOB_BACKOFF_SCHEDULE_MS` = 1 minute → 5 minutes → 30 minutes (cap; every attempt beyond the 3rd reuses the 30-minute cap). `DEFAULT_JOB_MAX_ATTEMPTS` = 5 — a job that fails a 5th time is marked permanently `failed`, not retried again.
- **Lifecycle**: `pending` → (claimed by a worker) → `running` → `done` | back to `pending` with a bumped `run_at` (retry) | `failed` (attempts exhausted). `claimDueJobs` claims atomically (so two workers can't double-process one row); `reclaimStuck` resets any job stuck in `running` past a staleness window (default 5 minutes) back to `pending`, recovering from a worker that crashed mid-execution without ever calling `markDone`/`markFailedOrRetry`.
- **Dedupe**: `enqueue` takes an optional `dedupeKey`; a partial unique index on `jobs(dedupe_key) WHERE dedupe_key IS NOT NULL` makes a second enqueue with the same key a no-op, coexisting freely with the many jobs that never set one.
- **The poller** (`apps/server/src/jobWorker.ts`): `startJobWorker()` runs `runOnce()` on a `setInterval` (default `JOB_POLL_MS`, see Environment above; `.unref()`'d so it never holds the process open on its own). `runOnce()` never throws — every failure mode (a throwing handler, an unregistered job type, malformed JSON payload, even a DB error on reclaim/claim) is caught and turned into either a per-job retry/failure or a logged-and-swallowed cycle-level error. `registerJobHandler(type, handler)` is the handler registry, populated once at boot (`index.ts`) before `startJobWorker()` runs — registration must happen first so the very first poll cycle already knows how to handle a job left `pending` from before a restart.
- **The migrated follow-up**: the 1-hour critical/high check-in nudge (`messageHandler.ts`'s `CHECKIN_FOLLOWUP_JOB_TYPE` = `'checkin_followup'`, handler `sendCheckinFollowup`) used to be a raw `setTimeout(..., 3600000)` — now it's `db.enqueueJob({ type: 'checkin_followup', payload: { phone }, runAt, dedupeKey })`, called from the same call site in `handleIncomingMessage`. `dedupeKey` buckets by phone + wall-clock hour (`checkin_followup:<phone>:<YYYY-MM-DDTHH>`), so several qualifying messages from the same user within one hour schedule only one follow-up — a dedupe guard the old `setTimeout` never had. **Delivery is at-least-once, not exactly-once**: a crash between the WhatsApp send succeeding and `markDone()` persisting causes a retry and could send a duplicate nudge. This is a deliberate, documented trade-off (see `sendCheckinFollowup`'s doc comment) — the cost of an occasional duplicate low-stakes reminder is judged far lower than the effort of building true exactly-once delivery for it.
- **Shutdown**: `index.ts` installs `SIGTERM`/`SIGINT` handlers that call `stopWorker()` (clears the interval) then `process.exit(0)` directly — it must exit itself because installing the handler replaces Node's default "terminate immediately" behavior for that signal, and `scripts/smoke`'s cleanup traps rely on a plain `kill <pid>` actually ending the process.
- **DPA erasure coverage**: `jobs.user_phone` (populated at enqueue time from a phone-shaped payload) is in `erasure.ts`'s `ERASURE_TARGETS` list — `DELETE /me/account` clears a user's pending/failed job rows same as every other user-data table. This was a gap in the original P4-A landing, closed in P4-B.

**Observability (P4-B).**

- **Structured logging + correlation ids** (`middleware/requestObservability.ts`, mounted first in `createApp()`): every request gets an `X-Request-Id` (honors a sane incoming header, else mints `crypto.randomUUID()`), echoed back on the response and included in the global error handler's JSON body. Exactly one `http_request` log line per request, emitted on `'finish'` — method, path, status, duration, request id; never the body or query string.
- **Metrics** (`apps/server/src/metrics.ts`, exposed at `GET /metrics` in Prometheus text format, no external dependency): `http_requests_total` / `http_request_duration_ms` (count/sum/max, by method+route-template+status-class), `http_server_errors_total` (only requests that reached the global backstop), `danger_escalations_total` (critical/high only, from `audit.ts#auditDangerEscalation`'s existing funnel), `llm_calls_total`/`llm_failures_total` (from the single LLM chokepoint), `otp_requests_total`/`otp_verifications_total`, `jobs_total` (gauge, sampled fresh from `countJobsByStatus()` on every scrape — omitted entirely rather than lying with zeros if that DB read fails), plus `process_uptime_seconds` and `nodejs_memory_*_bytes`. Gating: see `METRICS_TOKEN` in Environment above.
- **Health**: `GET /health` (liveness — must return instantly, never touches the DB or user data) and `GET /health/ready` (readiness — `SELECT 1`-style DB ping, `503` on failure so a host's readiness probe can act on HTTP status alone).
- **Global error handler** (`apps/server/src/errorHandler.ts`, registered last in `createApp()`, four-arg Express error middleware): a backstop, not a replacement — every route already wraps its own body in try/catch and returns its own error JSON, so in practice this mostly catches body-parser's synchronous JSON-parse errors plus (test-only, via `CreateAppOptions.enableTestErrorRoute`) a throwing route that exercises this file directly. Never leaks a stack trace or error message to the **client** — the response is always exactly `{error:'internal_error', requestId}`; the message is logged server-side through the redacting logger and passed to the alerting seam (which redacts it again independently).
- **Process-level safety net** (`index.ts`, installed before any boot work starts): `unhandledRejection` logs and keeps running (this codebase's own discipline — every route try/catches, the job queue documents "never throws" — means a truly unhandled rejection reaching here is a gap worth logging loudly, not worth crashing over). `uncaughtException` logs, alerts, then `process.exit(1)` so the host's supervisor restarts a clean process — safe specifically **because** of the durable job queue: any pending/mid-flight follow-up survives in `jobs` and resumes on the next boot, rather than being silently lost the way the old `setTimeout` would have been. Known limitation: `notifyCritical`'s webhook POST is fire-and-forget and not awaited before `process.exit()`, so on a genuine crash the webhook may not finish sending — the synchronous ERROR-level log line immediately before it is the reliable signal for that specific path.
- **Alerting is proportionate, not a platform** (`apps/server/src/alerts.ts`): `notifyCritical(event, context)` **always** logs one ERROR-level line (so host log-based alerting — Render/Railway/journal grep on `[ERROR]` — works even with zero configuration), and additionally POSTs a small PII-free JSON payload (`{event, message, requestId, timestamp}`) to `ALERT_WEBHOOK_URL` when set. Fire-and-forget with a 5s timeout; a failed/slow webhook is caught and logged, never thrown back into the caller (the global error handler and the job worker, both of which must never fail while already handling a failure). Callers: the global error handler on every backstop hit, and the job worker when a poll cycle's failure count crosses `JOBS_FAILED_ALERT_THRESHOLD`.

New table: `jobs` (`packages/adapters/src/sqlite/connection.ts`) — `type`, `status`, `payload` (JSON text), `run_at`, `attempts`, `dedupe_key`, `user_phone`, `locked_by`.

## Non-obvious points

- **Danger-sign triage is deterministic and duplicated on purpose.** The engine is `packages/core/src/dangerSigns.ts`, pinned by the 60-entry golden fixture. The PWA carries a verbatim CRITICAL/HIGH mirror (`apps/web/src/lib/localDangerSigns.ts`) so offline-queued entries escalate instantly client-side; `tests/offlineDangerSignsParity.test.ts` fails if the two drift. Change a CRITICAL/HIGH pattern in core → copy it to the mirror. (apps/web can't import `packages/core`: no package.json there, and apps/web's standalone tsconfig doesn't share the root path aliases.)
- **Danger signs escalate regardless of consent — vital interests, load-bearing.** CRITICAL bypasses the consent gate entirely (checked before consent state is even loaded); HIGH/MODERATE danger copy is still prepended to a `consentRequired`/gate response. See "Consent, audit, and data-subject rights" above for the full mechanics. Never let consent enforcement move ahead of, or suppress, an escalation.
- **Post-delete read hardening (P3-E): a stateless bearer token outlives `DELETE /me/account`.** Tokens are HMAC-signed phone numbers (`auth.ts`), not session records, so a token issued before a delete still verifies fine afterwards — nothing to revoke server-side. Before P3-E, `GET /me` and `GET /me/export` called `userManager.getOrCreateUser()`, which would silently recreate a blank `users` row on the very next read after deletion (P3-C flagged this; P3-D's Profile delete flow only mitigated it client-side, via `clearSession()` + redirect). The fix (`userManager.ts#getUserForRead`, used by `GET /me` and `GET /me/export`; a lighter inline guard in `GET /me/consent` and `GET /me/activity`, which never created rows to begin with) needs to tell apart two states that look identical from "does a `users` row exist?" alone — a phone that never signed up (safe to auto-vivify, preserving the legacy `/auth/login` demo path and any brand-new-user test) vs. a phone that signed up and was later deleted (must NOT be resurrected). It tells them apart via `audit.ts#wasAccountDeleted()`: since `eraseUser()` deliberately leaves `audit_log` alone, a retained `delete`/`account` row for that phone is proof positive the account existed and was erased — regardless of when. The guard is always "row missing now AND was deleted before", never "was deleted" alone, so a phone that legitimately signs up again later (a fresh `POST /auth/otp/verify`, which still creates the row unconditionally — untouched by this fix) isn't locked out just because its audit history still remembers an old delete. All four routes answer a deleted account's stale token with `401 { error: 'no_account' }`; `apps/web/src/lib/api.ts`'s `authedFetch` already treats any 401 as a hard logout (`clearSession()` + redirect to `/login`), so no web client change was needed. Pinned end-to-end in `tests/postDeleteReadHardening.test.ts`.
- **Single LLM chokepoint.** Only `packages/adapters/src/llm.ts` may import `openai`. Its `chat()` redacts every user/assistant message via core `redactForLLM` (phones, emails, userinfo-URLs, 11+ digit runs, and the user's full stored name); system prompts pass untouched and are the one place allowed to carry the user's FIRST name only. The policy rationale lives in `packages/core/src/redaction.ts`'s header.
- **Repository pattern is the Postgres seam.** Interfaces in `packages/core/src/repositories.ts`, SQLite implementations in `packages/adapters/src/sqlite/`, and `apps/server/src/database.ts` re-exports stable function signatures. A future Postgres port implements the same interfaces in a new adapter; app code shouldn't change.
- **One journal shape, two writers.** The WhatsApp stage machine and the PWA form (`POST /journal/entries`) write the same `journals` columns; `physical_symptoms` is a JSON-array string, `'none'`, or raw text — parsers in core handle all three, so summaries/reports/trends work on rows from either source. The form re-runs `detectDangerSigns` over symptoms+text+note; it is never a triage bypass.
- **Idempotency + offline outbox.** `POST /journal/entries` dedupes on (`user_phone`, `client_entry_id`) via a partial unique index; replays return the saved entry with `deduped: true` (escalation recomputed so a retry never drops the safety banner). The PWA queues failed submissions in IndexedDB (`apps/web/src/lib/outbox.ts`) keyed by the same `clientEntryId`; reads are stale-while-revalidate from IndexedDB (`offlineCache.ts`). Background Sync is a wake-up hint only — the app-layer flush is the guarantee.
- **`/chat` and `/insights` are both a page route and an API path** in the Next app. `next dev` disambiguates with `beforeFiles` rewrites gated on the `X-Amaaii-Api` header, which `apps/web/src/lib/api.ts` sets on every API call. The static export has no rewrites — it prefixes `NEXT_PUBLIC_API_ORIGIN` instead (empty/same-origin in the single-process deployment). **In Express itself only `/insights` collides** — Express routes by method, and there's no `app.get('/chat', ...)` (only `POST`), so a GET to `/chat` falls straight through to the exported `chat.html` with no ambiguity. `GET /insights` is explicit on both sides (page AND API), so `app.ts`'s handler checks `X-Amaaii-Api: 1` OR an `Authorization` header first; if neither is present it calls `next('route')` to fall through to the static export instead of running `requireAuth`.
- **SW must not cache API GETs.** `apps/web/public/sw.js`'s `API_GET_PATHS` (incl. `/insights`) bypasses the service worker so a flaky connection can't hand JSON callers the cached offline HTML page; `tests/swApiGetPaths.test.ts` pins the list.
- **Old-PWA service-worker takeover.** A browser that visited the retired `public/` app has a SW registered at scope `/` under `amaaii-shell-v6`. The new `apps/web/public/sw.js` registers at the exact same URL (`/sw.js`) and scope (`/`) — `ServiceWorkerRegister.tsx` and the old `public/app.js` both called `navigator.serviceWorker.register('/sw.js')` with no explicit scope. Because the bytes differ, the browser detects a new SW on the next registration check, installs it alongside the old one, and both scripts call `self.skipWaiting()` — so the new worker activates immediately instead of waiting for old tabs to close. Its `activate` handler deletes every cache key that isn't its own current `VERSION` (`amaaii-web-shell-v2`), which is a plain `!==` check against ALL cache names — not a prefix match against its own naming scheme — so it already purges the old app's `amaaii-shell-v6` cache along with any of its own previous versions, with no extra code needed. `self.clients.claim()` then hands control of open tabs to the new worker without a reload. `Cache-Control: no-cache` on `/sw.js` (set in `app.ts`'s static serving) matters here too — without it, an intermediate HTTP cache could keep handing the browser's update check a stale copy of the script, masking the byte diff that triggers this whole flow.
- **Onboarding is stateless** — it re-reads the user row each turn and infers the next question from the first null column (`name` → `age` → `pregnancy_week` → `location`), with a 3-strikes LLM fallback for unparseable name/week answers. Don't add a separate onboarding state machine.
- **OTP design:** `otp_codes` table stores only `HMAC-SHA256(phone:code)` (never plaintext), 10-min expiry, 5 verify attempts, 3 sends per rolling hour. Pure decisions in `packages/core/src/otp.ts`; crypto in `apps/server/src/otp.ts`.
- **The SQLite file is NOT committed** (`*.db` is gitignored; `git ls-files` shows none). `./amaaii.db` is created/migrated at boot by `initializeDatabase()`. Tables: `users`, `conversations`, `symptoms`, `anc_visits`, `journals`, `journal_sessions`, `medical_history`, `otp_codes`, `consents`, `audit_log` (Phase 3), `jobs` (Phase 4 — see above). A local `./amaaii.db` may back a live demo server — use a scratch `DB_PATH` for anything experimental.
- **System prompt doctrine** lives in `amaaii_ai_prompts_guardrails.md` and is partially duplicated in `apps/server/src/amaaii.ts`. The safety rules (never diagnose, never prescribe, escalate danger signs, Kenyan/Kiswahili context, triage never touches the LLM) are load-bearing — don't soften them casually.
- **Check-in follow-up delivery is at-least-once, by design — not exactly-once.** The `checkin_followup` job's handler (`sendCheckinFollowup`) sends the WhatsApp message, THEN calls `markDone()`; a crash between those two steps causes the job worker's normal retry path to re-run the handler, which could send a second, duplicate "how are you feeling" nudge. Accepted trade-off (see `messageHandler.ts`'s doc comment on `sendCheckinFollowup`): building true exactly-once delivery for one low-stakes reminder message was judged disproportionate. The `dedupeKey` (phone + wall-clock hour bucket) prevents a *different* kind of duplicate — several qualifying messages in the same hour scheduling separate follow-ups — but does nothing about this crash-window case; don't conflate the two guards.
- **Metrics label cardinality is a closed vocabulary, checked by test.** Every label value `metrics.ts` accepts anywhere is either a route TEMPLATE (never a raw path with ids/query params), a status CLASS (`2xx`/`4xx`/`5xx`, never an exact code), or a small fixed set of urgency/job-status/OTP-outcome strings — never a phone number, name, or free-text message. This is what keeps a Prometheus scrape from becoming an unbounded, PII-leaking series explosion; `tests/observability.test.ts`'s "PII-free" assertion pins it against regressions, not just the comments in `metrics.ts`'s header.
- **Jobs are in the DPA erasure cascade — this was a real gap, not a hypothetical.** P4-A's original `jobs` table landed without an erasure hook; a deleted user's still-pending `checkin_followup` job would otherwise survive `DELETE /me/account` and fire afterward. Closed in P4-B: `jobs.user_phone` is populated at enqueue time and is in `erasure.ts`'s `ERASURE_TARGETS`, so erasure clears it like every other user-data table. If a future job type's payload never carries a phone-shaped value, its `user_phone` stays `NULL` and it's simply untouched by erasure — same as any other WHERE-scoped delete.

## Aspirational vs. actual stack — important

`CLAUDE_CODE_PROMPT.md` describes a planned rewrite on **Python / FastAPI / PostgreSQL / Anthropic Claude / WhatsApp Business API**. None of that is implemented. The live code is **TypeScript / Express / SQLite / OpenAI GPT-3.5 / Twilio WhatsApp sandbox**, plus the Next.js PWA. Treat `CLAUDE_CODE_PROMPT.md` as a spec for a future port — don't refactor toward it without explicit instruction.
